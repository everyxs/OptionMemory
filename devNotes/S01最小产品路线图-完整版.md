## 一、总目标

以 S01 和 HEA-Lens-1540 为贯穿案例，完成两条相互衔接的能力线：

### 1. OptionMemory 原能力线

```text
多源数据
→ facts / rules / options / models
→ Horn 闭包与 J/≺
→ 修订传播
→ 冲突治理
→ Option 注册、结算与认证
→ DSH / OpenCode 双 host
```

### 2. LLM 原生 Planner 增量线

原生 DSH/OpenCode 对话与后台任务模式：

```text
对话请求
→ 简单任务在会话内同步完成；长任务提交到共享 planner-runtime
→ 返回 plan_run_id
→ 结构化决策 + decision gate + Option 执行
→ 原生 question / permission ask / ctx.userQuestions
→ observations / outcomes / model critique
→ 重规划、认证证据与 RL-ready 轨迹
→ 任一 host 查询、回答、停止或在 Option 边界受控接管
```

SuperAgent 完整持续宿主模式：

```text
Source / Trigger / 人工输入
→ SuperAgent Eval + Policy + Mandate
→ Ticket + Assignment
→ OptionMemory Executor Adapter
→ plan_run / Planner 决策 / Option 执行
→ SuperAgent Attention / Report / Outbox
→ OptionMemory 校准、认证、撤销与后续重规划
```

最终系统不仅保存“知道什么、为什么可信”，还能够由版本化 LLM Planner 决定“接下来做什么、由哪个 Option 执行、失败后如何调整”。DSH/OpenCode 通过同一个共享 planner-runtime 获得有限生命周期的持久化后台任务能力，不各自建设完整持续任务平台；SuperAgent 负责开放生命周期的长期 Source 监听、持续接单、Ticket 恢复和人工后续消息路由。

## 三、统一架构

### 3.1 资产与运行职责

```text
        Conversation / Continuous Host Adapter
          DSH / OpenCode / SuperAgent
        submit / status / stop / answer / report
                           │
                           ▼
                Planner（plan_run 内唯一规划控制面）
                           │
                           ▼
subtask ───────────→ option ───────────→ model
目标与交付要求       能力契约 + 执行实现    Option 级世界模型
                       │                 anticipation/critique
                       ▼
                  option_event
```

| 资产/组件 | 职责 |
|---|---|
| subtask | 目标、上下文、交付要求和约束 |
| option | 统一承载 tool/skill/api/llm_workflow/subagent/device 执行 |
| model | Option 级语义世界模型、证据、经验、评价和已知局限 |
| planner | 版本化 LLM Agent，负责分解、选择、重规划、等待和停止 |
| shared scheduler | DSH/OpenCode 共用的后台执行组件，负责 plan_run、inbox/outbox、内部 timer、lease、幂等、唤醒和恢复 |
| host adapter | 将宿主的 submit/status/stop/answer 或 start/deliver/stop/report 映射到统一 plan_run 契约；复用原生交互，不复制业务逻辑 |

Option 是 OptionMemory 内部唯一的对外动作执行面。代码中的 option executor 和 SuperAgent Executor Adapter 都只是内部实现，不新增 Executor 领域资产。Planner 和 Model 的内部推理智算不递归包装成 Option。

### 3.2 Planner 决策与权限边界

```text
execute / decompose / replan / retry / wait / ask / stop / ignore
```

- `execute` 由 Option 落实。
- 控制决策由 Planner 作出，经 decision gate 后由共享后台运行时或持续宿主落实。
- Planner 不直接修改外部世界，不通过文本扩大授权。
- 父 Planner 是 plan_run 内单一逻辑控制面；同一 subtask_event 的决策串行化。
- SuperAgent Eval 只负责接单、授权和路由，不与 OptionMemory Planner 同时规划同一 Ticket 的实现方案。
- SuperAgent 的人工 stop 是外部持续任务的权威终止信号；OptionMemory 的 Option revoke 只改变能力可用性，二者不得混用。

### 3.3 原生 Attention 与审批复用

- **OpenCode**：语义澄清使用原生 `question`，操作审批使用 permission ask 与对应 hook。
- **原生 DSH**：使用 `ask_user_question` / `ctx.userQuestions` 与 approval intent；目标版本支持时可用 `askTimed`、pending/continued 和 Remote `answer`。外部 planner-runtime 必须经 DSH root Session/Adapter 提问，不得冒充 Agent 或绕过 delegated caller 限制。
- **SuperAgent**：使用 Ticket Attention、Report.question、原会话 Outbox 和后续 Input。
- **planner-runtime**：只保存 `ask/wait_condition`、`host_question_ref`、`answer_event_id`、plan_run 恢复和防重关联，不新建问题卡片、回答 UI、通知系统或权限审批引擎。
- 宿主掌握其原生问题/审批交互生命周期；MemoryCore 保存 plan_run 等待条件及回答证据投影，不复制一套同义 Question Center。

### 3.4 两种运行模式与状态归属

| 模式 | 宿主持有 | OptionMemory / 共享 runtime 持有 | 能力边界 |
|---|---|---|---|
| DSH/OpenCode 对话与后台任务 | 对话、原生 question/permission 状态、host Session 与工具状态 | 共享 plan_run、inbox/outbox、内部 timer、Planner/Option 事件、证据与认证 | 简单任务会话内完成；长任务跨 Session 持久执行，不提供完整长期 Source 接单 |
| SuperAgent 完整持续宿主 | Source/Ticket/Mandate/Assignment/Attention/Outbox、Subscription 和人工后续消息 | plan_run、Planner/Option 事件、证据与认证；不另建 Ticket 生命周期 | 长期监听、持续接单、Ticket 恢复与人工 Attention |

SuperAgent 模式中的 Assignment 对应一次 plan_run/attempt，而不是单个 option_event。一个 plan_run 可以包含多次 Planner 决策和多个 Option 执行。plan_run 是内部运行上下文标识，不是与 Option 平行的新领域资产。

共享 plan_run 允许跨 harness 查询、回答、停止和受控接管。接管只在 Option 边界进行，先暂停新分发并完成副作用对账，再校验目标宿主授权与能力、原子转移 lease；不迁移宿主专有权限、工作目录或后台进程，不盲目重放外部副作用。

### 3.5 Option 级 Model

Model 保留世界模型职责，但不要求传统数值 T/R 是 LLM 调用的前置条件：

```text
reasoning_spec  → anticipation：预期效果、风险、未知项
evidence_spec   → 必要证据、查询引用、成功/失败经验
evaluation_spec → critique：目标进展、质量、约束和结构化 verdict
```

未知模型能力保持 null/uncalibrated，不用 0 或生成的说明冒充已知。SuperAgent 的 ready Report、OptionMemory Model critique、CI/PR 结果和人工验收分别记录来源，任一自我报告都不得单独冒充独立外部验证。

### 9.1A 字段权威审计与增量精简迁移（2026-11-15 追加，P4-0）

在持久化队列和 Option Executor 实施前，先处理已识别的字段重复与未知值语义。该任务已批准纳入 Phase 4，但不是无条件删字段；每项精简必须先形成字段权威矩阵、兼容读取方案和回滚证据。

审计范围：

- `Option.model_binding` 与 `Model.option_id` 的双向绑定，确定权威外键和一致性修复方式；
- Model `j_records` 与 governance 事件 J 的双向关联，明确事件权威和查询投影；
- `calibration_history` 与成功率、预测误差、成本摘要，区分证据明细和派生快照；
- `theta_version` 与 `lin_theta` 的版本语义；

- SuperAgent 拥有 Source、Thread、Ticket、Mandate、Assignment 外部生命周期、Subscription、follow-up ownership、Attention、Channel Outbox 和人工 stop。

详细实施见 `devNotes/Week15-16开发手册-生成认证与SuperAgent持续适配.md` P6-4。

### 11.5A 增量验收

- 父 Planner 能在授权范围内主动分解、调度和重规划。
- 原生 DSH/OpenCode 与 SuperAgent 承接的生成和认证过程均可回放完整决策与执行轨迹。
- 不同 baseline 和证据来源可隔离统计。
- RL-ready 导出不虚构状态、reward 或下一状态。
- simulated/sidecar 不进入真实认证成功率。
- 原十工具、生成、认证和 R4 边界不回归。
- 长期 Ticket 的维护候选、Attention 批准、人工 stop、跨 harness Recall/修订/恢复通过；认证不混用 simulated/sidecar 或抽取器自评，原 10 工具不变。

### 11.6 后续可选：MCP server 评估（不纳入本 16 周 MVP 新增交付）

## 十二、统一事件与图模型

```text
subtask
   ▲
subtask_event
   ▲
plan_run / attempt（运行上下文，不是 Executor 领域资产）
   ▲
planner_event ─────→ planner
   │
   ├─ planner_event_decision
   ▼
option_event ─────→ option ─────→ model
   │                                │
   ├─ option_event_observation      │
   ├─ option_event_outcome          ▼
   └──────────────────────────→ model_event
```

Datalog 负责硬关系、门控候选和证据检索；LLM 负责语义判断。J/≺ 表达逻辑推导和修订，Planner 事件表达决策过程，二者通过 ID 关联而不混用。

SuperAgent 的 Ticket、Assignment、Trigger 等外部 ID 作为关联标识写入事件上下文，不回写或替代其权威状态。原生 planner-runtime 的 inbox/outbox 与 SuperAgent Effects/Outbox 分别服务各自运行模式，不做跨存储的同义复制。

单链查询使用 Datalog；大规模校准和统计优先采用固定查询加应用层聚合，避免通用 facts 的多重全表自连接。

## 十三、Host 与部署策略

### 13.1 MemoryCore

统一保存资产、plan_run、Planner/Option/Model 事件、证据、认证、能力视图，以及原生运行模式的 mandate、inbox/outbox 和恢复状态，是规划与记忆治理事实的唯一来源。

SuperAgent 承接任务时，MemoryCore 不接管其持续任务事实；SuperAgent Store 与 MemoryCore 分别持有不同事实，不形成同义的第二套控制状态。

### 13.2 OpenCode 对话宿主

Phase 4 优先验证 primary Planner、工具权限、后台 subagent 和事件回流。插件 storage/scoped fiber 不等同于可靠调度队列。OpenCode 保持对话体验，语义提问复用原生 `question`，操作审批复用 permission ask；长任务通过 submit/status/stop/answer 接入共享 planner-runtime，不另建完整持续服务或 Attention UI。

### 13.3 原生 DSH 对话宿主

Phase 4 使用与 OpenCode 相同的 S01 切片验证 Planner、工具、subagent、事件和恢复语义。提问与审批复用 `ask_user_question` / `ctx.userQuestions` / approval intent；`askTimed`、continued 和 Remote `answer` 按实际 pin 探针。外部 runtime 必须经 root Session/Adapter 提问。DSH rc 与 OptionMemory 能力版本分别 pin，升级前执行全量集成测试。

### 13.4 共享 planner-runtime

DSH/OpenCode 共用一个独立后台执行进程，通过 MemoryCore HTTP 访问统一 plan_run 状态。它负责有限生命周期后台任务的持久化、恢复、内部 timer、跨 host 查询/回答/停止和 Option 边界 handoff，不依赖某个交互式 Session 存活，也不承担 SuperAgent 式长期 Source 监听与持续接单。

### 13.5 SuperAgent 持续宿主

Phase 4 只做隔离 Executor 兼容探针，Phase 5 才进行正式适配。SuperAgent 提供 Source、Ticket、Mandate、Attention、Outbox 和持续恢复；OptionMemory Executor Adapter 提供 Ticket 内部的规划与 Option 执行。

SuperAgent 公开代码是研究原型，不作为当前生产依赖。其 Ticket/Mandate/Attention 等设计可复用，实际适配必须独立验证版本、故障恢复、权限和数据保留，不要求引入其 SQLite Store 到 MemoryCore。

### 13.6 未来 MCP

MCP 是统一 OptionMemory 契约的可选 transport，不是统一各 harness 运行时的前提，也不替代原生 hooks。是否立项沿用触发条件评审，不改变本 16 周 MVP 的原生双 host 交付边界。

### 13.7 后续治理：训练评价 Option 与外部 verifier（未立项）

**2026-11-15 讨论归档。** 当前 Phase 3 只批准并验收固定 `source_priority`：experiment > simulation > literature。后续可引入独立训练评价 Option 和外部 verifier，使裁决更自动化，但“更权威”仅限定于经过授权、独立验证的 baseline/context，不来自 Option 自评或外部服务名称本身，也不扩大当前 MVP 交付承诺。

#### 策略层次

- `source_priority`（当前）：严格来源优先级才自动 settle/revoke，未知或同级来源转人工。
- `option_score`（后续）：独立评价 Option 返回候选评分和不确定度，Model 提供校准历史、误差与适用域；策略只在有效校准和明确阈值内自动裁决。
- `external_verifier`（后续）：独立实验服务、认证评价器或验证 API 返回结构化 verdict、证据与签名；策略验证身份、授权、时效和适用范围后执行。

训练评价 Option 和外部 verifier 都是**证据生产者**。OptionMemory governance API 仍是唯一状态变更入口，Planner 不得用文本代替 settle/revoke，verifier 不得直接写 facts/options/models，候选 Option 不得通过自评为自己赋权。

#### 评价与证据契约

评价输出至少包括：候选 fact/option ID、逐项分数或 verdict、不确定度、证据引用、评价 Option/verifier ID 与版本、baseline/context、评价执行事件、有效期；外部 verifier 增加签名或认证引用。配置按谓词声明单/多值 cardinality、单位与值归一化、策略模式、阈值、状态映射、异常处理和策略版本；凭据只以 `credentialRef` 引用。

Decision gate 必须验证：

1. 评价者与候选 Option 独立，评价 Option/Model 当前 `settled`，未 revoked、失效或出域；
2. 校准覆盖当前材料体系、测量方法和数据分布，阈值来自独立真实验证；
3. 证据来自真实 option_event_outcome、model_event 或 verifier 报告，版本和签名有效；
4. simulated、未验证 sidecar 和 97 条待复核记录不得进入真实裁决或认证成功率；
5. 分差不足、同级、不确定度过高、证据缺失、版本不匹配或出域时 `manual_review`；
6. verifier 不可用或超时转 `manual_review`，签名无效、身份越权或证据篡改时 `blocked`，不静默降级为自动猜测；
7. 请求、响应和最终治理事件按幂等键关联，可回放到评价 option_event、model_event 或 verifier 证据，重复请求不重复改变状态。

#### 启用步骤与独立验收

| 阶段 | 交付 | 关闭条件 |
|---|---|---|
| EV0：契约与影子模式 | 评价 Option/verifier 只给建议，与人工裁决对照 | 独立性、校准、签名、适用域和血缘通过；不自动改状态 |
| EV1：辅助裁决 | 人工确认评价结果后调用 settle/revoke | 阈值、异常分类、幂等、完整回放和人工 stop 通过 |
| EV2：有限自动裁决 | 在明确 baseline/context 和低不确定度范围内自动执行 | 错误来源不误选、评价者不自证、异常不自动判胜、证据隔离和撤销回归通过 |
| EV3：扩展适用范围 | 扩展谓词、材料体系或 verifier | 新增独立真实证据与全量回归通过，逐域签署，不默认继承授权 |

外部 verifier 的签名无效必须 `blocked`；结果不确定、超时、出域或不可用必须 `manual_review`。所有阶段保留原始事实、历史裁决和人工 stop，R4 阻塞、原七工具数量、既有 Phase 0–3 验收及宿主边界不变。

## 十四、质量红线

1. 不改写已完成步骤及其验收，不用 Planner 增量替代原基线交付。
2. Planner 不得直接执行有副作用的 Option，所有决策必须经 decision gate。
3. 不得只凭 prompt、Session、插件内存或 fiber 维持任务真实状态。
4. **同类事实只能有一个权威来源**；不得让 DSH/OpenCode/SuperAgent 与 MemoryCore 形成同义重复的任务状态机。
5. 同一 plan_run 不得由 SuperAgent Worker 和 OptionMemory Planner 同时规划；SuperAgent Eval 只负责接单、授权和路由。
6. 不得虚构源 Agent 的 subtask、model、rationale、reward 或 plan。
7. 不得将 simulated/sidecar 未验证轨迹混入真实认证证据，也不得把 ready Report 直接等同于独立外部验证。
8. 不得让主动事件越过 mandate、预算或人工 stop；能力认证不得扩大行动授权。
9. 不得因 Planner 或 SuperAgent 适配改变 R4 阻塞和原插件工具数量。
10. 不得把一次正常演示当作可靠调度验收，必须执行重复 start/deliver、决策后、Option 执行中、Report 前崩溃和恢复测试。
11. 不得为迁移删除或重建既有 RocksDB 数据；SuperAgent 探针使用独立数据目录。
12. SuperAgent 人工 stop 与 OptionMemory Option revoke 不得混用；任何 host 不得绕过另一方的权威边界。
13. 不得另建宿主无关的 Attention UI、Question Center 或权限审批来替代 OpenCode question/permission、DSH userQuestions 和 SuperAgent Ticket Attention；DSH/OpenCode 不得各建一套权威调度器。
14. 跨 harness handoff 只能在 Option 边界进行，不得同时存在两个有效 lease，不得自动迁移宿主授权或在副作用未对账时重放 Option。
15. P4-1M 之后所有增量必须执行 `docs/memory-regression-acceptance.md` 共享回归，并增加本增量的记忆交互场景；P4-1M 的双会话结果不能作为后续免测证明。
16. 每次发布分别归档增量功能、记忆交互、真实宿主事件、质量/安全指标和未实现项；重复注入/写入、跨项目泄漏和自动 AGENTS 修改必须为 0，缺一类证据不得签署。
17. 日常记忆召回不得提升证据等级或扩大 mandate；R4、97 条待复核记录、原 Markdown 和既有治理历史不得被召回或修订流程静默改写。

## 十七、后续研发计划：dataStore 大体量数据模块

> 定位：dataStore 是独立的**大体量数据访问与批处理模块**，为 Planner 提供高层数据 Option，不成为新的 Planner、调度器或治理中心。该计划依据 `backups/ai-materials-raw-data` 的真实数据需求追加，**不扩大当前 16 周 MVP 的交付承诺，也不替代 S01/HEA-Lens 的既有验收**。
>
> 当前备份包含采集脚本、报告、字典与索引，但未包含 `data/matbd`、`data/corrdata`、`data/mged` 的原始数据或 10.6 GB 分卷。正式实施前必须先恢复只读数据快照并校验 SHA256；在恢复前只允许契约设计与只读索引探针。

### 17.1 数据需求与模块目标

需要支持的真实工作负载包括：

- matbd 约 156 万条文献/专利元数据的流式读取、字段裁剪、去重与质量统计；
- corrdata 11,181 条 test_report 及关联 HTML/JSON/图片的解析、引用与样本构造；
- mged 公开子集处理与需登录数据的明确拒绝；
- 55,531 个文件级索引、10.6 GB 原始文件和 Release 分卷的恢复、校验与引用；
- 清单计数口径核对、内容级去重、断链与空值检查、VLM 样本集生成；
- 后续受限增量补抓、跨 harness handoff 和可恢复的数据处理。

模块目标是避免把大体量原始数据、全量文件索引和批处理逻辑塞入 MemoryCore/Planner，同时复用现有 Python 采集脚本和数据资产。

### 17.2 与 MemoryCore / Planner 的边界

| 组件 | 权威职责 |
|---|---|
| dataStore | 原始文件、FILE_INVENTORY、物理 Schema、文件偏移与采集游标；行过滤、列投影、切片、聚合、join、RecordBatch 流式输出；行数、哈希、空值、重复候选和断链等技术测量 |
| MemoryCore | snapshot/raw/sample_set 引用、语义映射、合规与授权、质量判断、J/≺、修订、plan_run、决策与 outbox、Option outcome、认证和治理事务 |
| planner-runtime | 选择并执行 dataStore Option，维护 plan_run 状态、等待、取消、handoff 与恢复；不直接实现具体解析、SQL 或文件处理 |
| DSH/OpenCode/SuperAgent | 提供对话或持续任务宿主及原生 Attention；不直接持有 dataStore 的业务数据副本 |

核心纪律：

- **dataStore 负责“测到了什么”，MemoryCore 负责“能否使用、如何修订、是否认证”。**
- dataStore 不直接写 mnestic，只通过受控接口返回 `FactCandidate[]`、`quality_observation`、`raw_ref/snapshot_ref/sample_set_ref` 和幂等事件。
- 原始 HTML、图片、大型 JSONL、VLM 样本全集和完整文件索引保留在 dataStore；MemoryCore 只保存治理所需引用、摘要与精选事实。
- dataStore 的技术游标与 MemoryCore 的规划检查点通过 ID 关联，不混为同一种状态。

### 17.3 接口设计

```text
StorageBackend（必需）
  open / read / write / stat / glob / list / hash

QueryEngine（可插拔）
  scan(columns, filters, batch_size)
  aggregate(metrics, filters)
  join(left, right, keys)
  输出 RecordBatch 或普通行迭代器，不向 Planner 暴露后端专用连接或 SQL 方言

SnapshotAccess
  restore / verify / describe / export

IngestionBridge
  FactCandidate[] / quality_observation / raw_ref / snapshot_ref / sample_set_ref
```

默认技术组合：

- **fsspec**：本地、NAS 和对象存储的统一文件访问、缓冲、压缩与缓存；
- **PyArrow**：行过滤、列投影、切片、简单聚合、join 和 RecordBatch 流式处理；
- **Parquet**：只对需要反复查询的规范化投影按需生成，利用列裁剪、过滤与分区扫描；
- **DuckDB（可选）**：仅当复杂 SQL、频繁即席查询、跨源关联或实测性能不足时启用，不作为架构依赖；
- **Data Package**：数据集快照、资源、来源、版本与 license 描述；
- **Croissant**：后续 VLM 样本集、RecordSet、字段和 split 描述；
- **OpenLineage（可选）**：采集与转换运行事件的互操作导出，不替代 MemoryCore 的 J/≺。

现有 Python 采集器可作为 dataStore worker 复用，Node/TypeScript 宿主通过受控 API 调用。若未来要求全 TypeScript 实现，须单独评估 DuckDB/OpenDAL 的 Node binding，不提前锁定。

### 17.4 分阶段研发计划

### 17.4A 测试数据与场景（DG-01–DG-06）

新增场景只扩展 dataStore 的真实数据覆盖，不替换或放松 S01、R3 与 Option 既有 45 项验收，也不修改生产 J 边。原始快照恢复前，DG 场景只允许契约与索引检查，不设为当前必过验收。

| 场景 | 数据与验证重点 | 通过条件 |
|---|---|---|
| DG-01：快照与清单口径一致性 | FILE_INVENTORY、README、data/README、DATASET_INDEX 的快照与统计口径 | 区分 file/JSONL line/business record/detail/image；55,531/55,551 等差异可追溯到快照与文件，不合并成单一“正确总数”，不误判为多来源冲突 |
| DG-02：大文件流式处理 | matbd 大型 JSONL 的分批过滤、投影、聚合与 join | 不执行全量 `to_table`；内存有界、结果可复现、重跑幂等；不把 156 万条记录作为 Mem/CI 入库前提 |
| DG-03：实验报告解析与图文关系 | corrdata/test_report 的列表、详情、字段、正文、图片及 J/≺ | 原始页/字段/图片/构造版本可回放；多图页面只记同页共现，不冒充一对一标注；断链、缺失图片与空字段分别记录 |
| DG-04：授权与失败分类 | mged/corrdata 的 401、403、404、500 和 200 空表 | 各类状态分别记录；不登录、不求解 PoW、不绕过限制；公开子集不表述为全量获取；持续补抓遵守限速、重试上限与人工 stop |
| DG-05：断点续抓与跨 harness 对账 | `_id`、`data_id`、source_cursor、文件哈希、限速预算和输出清单 | 中断与 handoff 不重复请求、下载或 facts；部分平台失败标 partial，不冒充完整成功 |
| DG-06：样本集构造与认证 | 原始页/字段/图片、清洗值、样本值、构造器版本与 split | 样本血缘完整；近重复样本隔离；train/validation/test 可回查；自生成样本不作为独立外部正确性证据 |

禁止事项：不把 ref_smix 与 ref_smix_v2 当作 Phase 3 多来源冲突，不把 g_company 的 500 当作数据冲突，不把 MD5 相同直接当作语义重复，不把 604/97 混成单一认证成功率，不在单元测试执行真实登录或网络采集。

### 17.5 首期最小交付切片

1. 恢复并校验一个只读数据快照；
2. 使用 fsspec + PyArrow 读取 FILE_INVENTORY，完成口径核对；
3. 流式解析 corrdata/test_report，输出 `FactCandidate`、质量观测和血缘引用；
4. 对 matbd 大型 JSONL 做只读、分批、内存有界的过滤与聚合；
5. 验证 mged 未授权数据被阻止且无任何登录/PoW 行为；
6. 将一个离线清洗任务接入共享 plan_run，验证失败恢复和 MemoryCore 治理事务。

### 17.6 非目标与启用约束

- 不在首期导入全部原始数据、构建全量闭包或训练 VLM；
- 不把 dataStore 建成第二套 MemoryCore、Planner、任务队列或治理元数据中心；
- 不向 Planner 暴露任意 SQL、裸文件写入或绕过授权的数据访问；
- 不因 fsspec 支持文件事务就将其用作持续任务数据库；PyArrow Dataset 也不提供 ACID 保证；
- 不把 PyArrow join/group_by 当作天然全外存计算，必须以分批和实测内存为准；
- 不引入 DataHub/OpenMetadata、Iceberg/lakeFS 或第二个向量数据库，除非后续规模、协作或索引需求单独评审通过；
- dataStore 的接入不得改变原 Phase 0–2 验收、R4 阻塞、原插件工具数量以及 DSH/OpenCode/SuperAgent 的宿主边界。
