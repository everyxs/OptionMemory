# S01 最小产品路线图（OptionMemory 版）

> 基于课题1 PPT 中的 AlCoCrFeNi 高熵合金试样 S01 案例，制定一份可逐步实现的最小产品路线图。
>
> 目标：用 16 周时间，跑通「多源数据 → data 层 → declarative knowledge（Horn 闭包）→ 血缘（J/≺）→ 修订传播（变更代数）→ 冲突消解（governance 门控）→ option 注册与结算 → ω_certify 首个能力认证闭环」的最小通路。
>
> **交付形式：Phase 3 提前交付 DSH 与 OpenCode 两种 host 记忆模块，后续 Phase 以统一能力版本迭代**——遵循 26-03《DSH插件分解方案与记忆层详细开发方案》规范：
>
> - **DSH 平台**：DSH v0.2.2-rc.1（2026-11-14 更新至 npm latest 标签；该版本仍为 RC，不称为 stable；升级前必须全量跑集成测试；插件 API 使用 `@deepseek-ai/cordis@~4.1.0` 与 `@deepseek-ai/dsh-tools@0.2.2-rc.1`）
> - **OpenCode 平台**：使用 `@opencode-ai/plugin` 自定义工具与 `.opencode/plugins/optionmemory.ts` 项目级入口；与 DSH 共用核心服务和首版 7 工具
> - **插件形态**：Node.js/TypeScript host 模块；Node.js ≥ 24.9.0 + pnpm，Python SDK 仅作为调用客户端而非插件运行时
> - **规范**：DSH 使用 `dsh.plugin.json` + 列表式 `cordis.patch.yml` + apply/inject/ctx.tools.register/ctx.memory；OpenCode 使用 Plugin hooks + zod 工具 schema + 只读查询防护
> - **连接形态**：mnestic 独立服务进程 + HTTP 客户端（默认；插件与引擎解耦，消除 Node ABI 兼容风险）
> - **对齐**：OptionMemory 通用版跨生态接入中的 DSH 位与 OpenCode host 位；框架交互分别收敛于 `src/plugins/dsh/`、`src/plugins/opencode/`
>
> 核心 API 自 Phase 0 起按 host 工具接口兼容设计。**Phase 3 两种 host 同发 v0.1.0（各 7 工具），Phase 4 迭代 v0.2.0，Phase 5 迭代 v0.3.0（增加 memory_why），Phase 6 迭代 v0.4.0（增加 query_achievable / certify，共 10 工具）**。不得提前注册未实现工具；插件能力版本、DSH rc 与 OpenCode 版本分开管理，每次 Phase 升级均须全量回归并验证 RocksDB 数据保留。
>
> **交付节奏修订（2026-10-31）**：将原定 Phase 6 的首次插件封装提前至 Phase 3；Phase 6 改为完整能力版本迭代，不再作为首次插件交付点。**坚持原生双 host，不在 MVP 建设 MCP server；以单一 host-neutral 工具契约、共享契约测试和跨 host 数据测试防止功能分叉，未来其他 Agent 框架优先通过新增原生适配层接入，MCP 仅保留为 §9.7 的可选评审项。**

## 一、S01 案例回顾

PPT 中 S01 案例包含（右列为五层落位）：

| 阶段 | 内容 | 五层落位 |
|---|---|---|
| 多源原始数据 | 文献 PDF（成分 AlCoCrFeNi）、实验记录（电弧熔炼 1600℃）、XRD 谱图、SEM 图像、拉伸曲线 | data 层 |
| 结构化事实 | `composition(S01)=Al₀.₂Co₀.₂Cr₀.₂Fe₀.₂Ni₀.₂`、`process(S01)=电弧熔炼`、`hardness(S01)=512 HV` | declarative knowledge |
| 机理规则推导 | XRD 峰位解析 → `phase_structure(S01, BCC+FCC)` | Horn 闭包 + infer option |
| 冲突检测 | 文献记载 450 HV ⊥ 实验测定 512 HV | ν-gate（L1 检测） |
| 治理结果 | 可信数据 + 质量标记 + 治理记录 | settlement/revocation + ≺ 谱系 |

本路线图以 S01 为贯穿案例，每个阶段都有可验证的 S01 相关交付物。同时引入一个稍大规模的公开 HEA 成分数据集作为**批量测试集**，用于验证系统在多记录场景下的写入、推导、检索性能。

### 五层双线定义（2026-11-18 讨论定稿）

```text
raw data 层（SKILL.md / notes / CSV，文件为权威）
    │ 统一摄入（parse_*，只读投影）
    ▼
data 层候选（DocumentProjection + fact_candidates，无执行资格）
    ├─ declarative 线：→ ν门（认识论门：真伪）→ facts → Recall 非指令注入
    └─ procedural 线：→ 注册门（授权门：package_hash + 人工批准 + mandate）
          → Option/Model 资产（probation → settled/revoked）→ OptionExecutor
```

- 分流点在 data → knowledge 晋升处，不在摄入时打标。四条红线：candidate ≠ capability；指令性正文不入非指令注入池；注册门处哈希域由文本 content_hash 切换为实现 package_hash；ν门（问真伪）与注册门（问授权）不可合一。
- 环流：上行经门晋升（procedural 重资产延迟建立），下行只索引不复制（校准归 Model 字段、流水归 option_event/outcome、叙述残留仅降维归档索引与跨域副产品两个窄场景），退役降维不删除（revoke → dormant 永久保留）。
- 实施分工与顺序（2026-11-18，v5→v5.3 最终安排）：**Stage A（W13–14，血缘尾件 W15a）= 可用记忆产品**——mds + skills、procedural 管理完整、**零 SuperAgent 依赖**（线1 = procedural 管理/S2；线2 = join/识别/血缘/降维 + DS0 后台启动；W14 末产品演示为出口）；**Stage B（W15b–20）= SuperAgent + runtime 链（线1，Phase 5 关闭 W18）∥ dataStore 独立数据线（线2）**。红线由 S1–S6 人际契约与测试强制。任务落位详见完整版 §3.1A/§10.4B/§11.5B 与 Dual-Track 手册 v5 Final §2.2。
- 治理层命名（2026-11-18）：subtask-option-model-planner 资产链 = **治理层**（工具为其宿主接口，不递归包裹自己）；知识层经 ν 门自治、数据层写借道治理层执行面。闭环判据与工具矩阵见 Dual-Track 手册 §6.5/§6.6。

### 9.7 未来可选：统一 OptionMemory MCP server（未立项）

**当前决策（2026-10-31）：坚持原生模式。** MVP 继续以 DSH / OpenCode 原生模块交付，不新增 MCP server，不为 Codex / Pi 承诺尚未核实的原生接口，也不引入额外服务进程。选择原生模式的理由是当前只有两个 host，原生 hooks（DSH ctx.effect、OpenCode compaction / 事件 / 权限）集成更深，部署和运维更简单。

MCP 的潜在价值是统一工具契约、只读防护与错误映射，降低后续支持 Codex、Pi 等框架的边际成本，并减少 host API 升级对客户端的影响。其代价是新增 server 生命周期、协议版本、日志与故障恢复工作；远程部署还会增加 transport、鉴权和网络安全复杂度。MCP 只提供标准工具/资源通道，不能替代原生 hooks，也不会自动消除工具 schema 漂移。

**启动评估的触发条件**（满足任一即可重新立项评审）：

- 需要支持的 Agent 框架达到 3 个及以上，或 Codex / Pi 成为明确交付目标；
- 原生适配层的工具 schema、错误映射或只读防护出现重复维护/漂移；
- host API 升级频繁影响客户端，统一 transport 的收益超过新增运维成本；
- 出现跨进程、跨语言或多客户端访问需求。

**若未来启动，建议范围**：

1. 先抽取 host-neutral 工具契约与共享契约测试，禁止把 MCP 建成第三份独立业务适配；
2. 首版仅做本地 stdio MCP server，与 DSH / OpenCode 原生模块共存，不替换原生 hooks；
3. 复用同一核心服务与 RocksDB，保持 facts、rules、J/≺ 和门控结果一致；
4. 远程 HTTP transport、鉴权、多客户端与部署运维另行评审，不纳入默认首版。

工作量初步估算（不含核心功能本身）：统一契约与 stdio server、当前工具接入、协议/集成测试和文档约 **5–8 人日**；跨 host 契约与数据一致性测试另约 **1–2 人日**；远程 HTTP、鉴权和多客户端另约 **3–5 人日**。以上仅用于未来规划，不构成当前 MVP 的交付承诺。

### 9.8 未来可选：实体索引与访问路径自演进（未立项）

**当前决策（2026-11-01）：smix/v2 全量自连接的性能问题暂缓处理。** 当前实测全量 Datalog 自连接中位耗时约 20.8 秒，仅影响批量对拍查询路径，不影响 R1–R3 已完成派生、J 血缘或部分验收结论。已验证的备选方案（两次谓词查询 + 应用层 Map 连接约 42.5 ms）只作证据保留，当前不改代码、不迁 schema、不物化新表。

后续若同类实体连接成为高频路径，可将“实体索引与访问路径优化”评估为系统级 Option 自演进对象，例如 `optimize_memory_access_path`：

- **输入 I**：慢查询日志、数据规模、读写比例、当前索引和正确性基线；
- **策略 π**：分析访问模式 → 提议查询改写、应用层 Map、物化报告或实体复合索引 → 沙盒验证 → 灰度应用；
- **结果 β**：查询结果完全一致、目标延迟下降、写入成本可接受、支持回滚。

可演进的是**访问策略**，包括 `(predicate, entity_id)` 索引、物化对拍报告、Datalog/Map/缓存路径选择，而不是实体身份本身。`entity_id` 必须由稳定、确定、版本化的业务规则生成，不得由优化器动态合并或随意更改；跨来源实体消歧应另立 entity resolution option 并单独取证。

启动评审的触发条件：同类连接成为高频调用、交互延迟影响主流程、重复维护多个临时查询绕行方案，或索引收益经读写基线证明大于写入与迁移成本。任何实施仍须经过 ν 门、版本/血缘记录、读写性能复测和回滚验证，不得为提速覆盖原始 facts 或绕开服务层。

### 9.9 未来可选：训练评价 Option 与外部 verifier 治理演进（未立项）

**2026-11-15 讨论归档。** 当前 Phase 3 仅实现 `source_priority`：experiment > simulation > literature，未知或同级来源转人工复核。以下内容是后续治理演进，不改变既有 450/512 HV 验收，不赋予任何 Option、Planner 或外部服务直接修改 facts/options/models 的权限，也不扩大 16 周 MVP 承诺。

#### 目标模式

| 模式 | 证据来源 | 自动化边界 |
|---|---|---|
| `source_priority`（当前） | 登记的来源等级 | 仅严格优先级可自动裁决；未知、同级和异常转人工 |
| `option_score`（后续） | 独立训练评价 Option 的结构化评分、Model 校准和适用域 | 仅在校准有效、分差与不确定度满足阈值时自动裁决 |
| `external_verifier`（后续） | 独立实验服务、认证评价器或外部验证 API 的 verdict 与证据 | 仅在授权、签名、时效和适用范围均有效时自动裁决 |

训练后的 Option 是评价动作执行面，Model 提供校准、误差和适用域；外部 verifier 通过 API Option 接入。二者都只提供裁决依据，最终状态变更必须继续经过 OptionMemory governance API 与 decision gate。

#### 统一评价契约与门控

评价结果应包含候选 fact/option 的分数或 verdict、不确定度、证据引用、评价 Option/verifier 及版本、baseline/context、执行事件、有效期；外部 verifier 还应包含签名或认证引用。不得只返回自然语言“谁更可信”，也不得由候选 Option 给自己评分后自行 settle。

自动裁决的必要条件：

- 评价者与候选 Option 独立，当前状态为 `settled`，未 revoked、失效或出域；
- 使用当前上下文已校准的真实证据，阈值来自独立验证，不凭经验设定；
- simulated、未验证 sidecar、97 条待来源复核记录不得进入真实裁决成功率；
- 分差不足、同级、不确定度过高、证据缺失、版本不匹配或出域时返回 `manual_review`；
- 外部 verifier 不可用返回 `manual_review`，签名无效、身份越权或证据被篡改时 `blocked`，不静默降级为猜测；
- 请求与响应按幂等键关联，governance 事件可回放到评价 option_event、model_event 或 verifier 证据。

广义策略配置按谓词声明 `cardinality`、单位和值归一化、策略模式、阈值、未知/同级/异常处理、胜败状态映射和策略版本。外部凭据只保存 `credentialRef`，不写入配置文件或事件明文。

#### 分阶段启用

1. **EV0 契约与影子模式**：评价 Option/verifier 只给建议，与人工裁决对照，验证独立性、校准、签名和完整血缘，不自动改状态。
2. **EV1 辅助裁决**：人工确认后调用 settle/revoke，验证阈值、异常分类、幂等与回放。
3. **EV2 有限自动裁决**：仅在明确 baseline/context、低不确定度和有效授权范围内自动执行，保留人工 stop 与撤销。
4. **EV3 范围扩展**：只有新增独立真实证据和回归通过后才扩大谓词、材料体系或 verifier 范围。

每个阶段必须独立验收：错误来源不会被误选、评价者不能自证、模拟/待复核证据被隔离、异常不自动判胜、重复请求不重复记账、原始事实与历史裁决始终可查询。R4 阻塞、原七工具数量和既有 Phase 0–3 验收边界保持不变。

## 十、与 OptionMemory 通用版的工程对齐

> 本路线图是 OptionMemory 通用版（[[04-创造层/项目/26-03 神经-符号具身智能智能体/项目开发文档/OptionMemory-长期工程规划|OptionMemory-长期工程规划]]）的**材料垂直实例**。工程上遵循通用版的系统结构、标准 API 与存储路线；材料特有选型明确映射如下，验证成熟的组件按 §10.5 回流通用版。

### 10.1 系统结构对齐

| 通用版四分结构 | 材料实例 |
|---|---|
| `memory/`（data_store / knowledge_graph / option_repository / model_calibrator） | mnestic 实例：两类公民 + rules 双层资产 + J/≺ + subtask/option/model 注册表 + procedural knowledge 表 |
| `runtime/`（option_selector / intra_option_executor / gate_controller） | TypeScript 应用层：planner 初版 + option 执行器 + ν 门 |
| `plugins/` | **materials 多 host 模块**——Phase 3 首次交付 DSH + OpenCode v0.1.0，Phase 4–6 迭代至 v0.4.0；DSH 使用 manifest/patch/apply，OpenCode 使用 Plugin hooks + zod 工具 schema + `.opencode/plugins` 入口；框架交互分别收敛于 `src/plugins/dsh/`、`src/plugins/opencode/`，核心逻辑零框架依赖，同一 facts/rules/J/≺ 与 RocksDB 数据不分叉 |
| `evaluation/OptionBench` | **OptionBench-M**（材料垂直实例，见 §七） |

### 10.2 标准 Plugin API 对齐

| 通用版 `OptionMemoryPlugin` API | 材料版实现 | 落地 Phase |
|---|---|---|
| `record(trajectory)` | data 层 observations 写入 + 解析 option 遥测 | P0 / P4 |
| `query_state(query)` | `memory_query`（Datalog） | P0 |
| `query_achievable(s, o, ε)` | `option_memory.query_achievable` | P6 |
| `decompose(goal)` | MVP 不做（subtask 手工定义）；完整产品 | — |
| `propose_option(evidence)` | `propose_option`（检验装置简化版） | P1 / P4 / P6 |
| `settle(id, validation)` | `settle`（结算协议初版） | P4 |
| `revoke(id, reason)` | `revoke`（ν 门 + TMS 级联） | P2 / P3 |
| `calibrate(belief, outcome)` | model 层结算折叠（成功率/误差更新） | P4 / P6 |
| `audit(probe)` | ≥200 场景正确性基准（OptionBench-M 雏形） | P6 后延展 |

材料版特有接口（`memory_set` / `memory_retract` / `memory_why` / `certify`）作为 materials 插件的领域扩展，动词命名遵循通用版规范；通用版新增标准接口时材料版按映射表跟进。

### 10.3 存储选型映射

| 通用版分层 backend                    | 材料版选型                             | 说明                    |
| -------------------------------- | --------------------------------- | --------------------- |
| event_store（JSONL / TimescaleDB） | 结算账本 JSONL + mnestic 事件流          | data 层遥测与 option 结算记录 |
| graph_store（CozoDB / Neo4j）      | **mnestic（CozoScript / Datalog）** | J/≺ 血缘、闭包、级联          |
| kv_store（RocksDB / Redis）        | mnestic RocksDB 后端                | 持久化                   |
| vector_store（Milvus / FAISS）     | mnestic 内建 HNSW（1024 维）           | 语义召回 + 实体对齐           |
| MVP 文件存储                         | P0–P1 可 JSONL 原型先行，P2 起切 mnestic  | 与通用版 MVP 路径兼容         |

升级触发条件遵循通用版 §4.3（option > 10k → KV 缓存；lineage 查询变慢 → 图库强化等）。

### 10.4 阶段对应

| 通用版路线 | 材料版对应 |
|---|---|
| Phase 0：OptionBench 协议定义（0–4 月） | OptionBench-M 场景清单与五探针接口定义（§八 行动项） |
| Phase 1：OptionBench V1.1 发布（4–8 月） | ≥200 场景正确性基准（P6 后延展） |
| Phase 2：OptionMemory MVP（8–12 月） | **本 16 周路线图 = 通用版 MVP 的材料垂直先行实例** |
| Phase 3：生态插件与 RL 治理（12–20 月） | materials 插件回流通用版；ω_distill 固化对应通用版 agent-level / token-level RL；物理 option（湿实验/实验室自动化）对应通用版 physical grounding 的材料实例 |

### 10.5 双向回流机制

- **下行（通用 → 材料）**：五层 schema、公民权六元组、变更代数、OptionBench 评价协议直接采用通用版规范，不做材料特化分叉。
- **上行（材料 → 通用）**：材料版率先验证的组件作为通用版候选设计回流——rules 双层资产、ω_certify 阈值标定方法、验证阶梯 fidelity schema、漂移/出域判别器、≥200 场景基准中的可迁移场景。材料版是通用版「垂直应用验证场」定位的工程兑现。

### 10.6 开发主线声明（2026-09-11 排查补，v2 修正）

**本 16 周路线图为 memory-core 的单一开发主线**；OptionBench V1.2 §4.6 的测量基础设施功能**不另立开发线**，按以下映射纳入本路线。**总原则：memory-core 能力只建一次；OptionBench 只做环境、接入、评分；共享点用契约对齐，不做两遍。**

| V1.2 测量功能 | 纳入本路线阶段 | 说明 |
|---|---|---|
| 镜像写入层（memory_set_batch + 幂等 + 审计 ν 门） | Phase 0（batch，Week 2）+ Phase 2（ν 门双模式） | OptionBench 切 audit 模式复用，不另建 |
| **事件 schema 最小集**（task/action/observation/outcome/drift 五类核心事件） | **Phase 2（Week 5–6，与 ν 门双模式同期）** | **设计对齐依赖**：OptionBench M2 阶段（≈W5–8）定稿接入协议 schema 时以此最小集为对齐基准，避免两套 schema 各自发明后再做转换层；运行期批量写入（M3 起，W9+）本就在此时点之后 |
| 事件 schema 完整类型体系（confidence/legality/grounding/plan/skill…） | Phase 4（随解析遥测扩展） | OptionBench 投影 schema 为其子集；**一套 schema，两处使用，禁止分叉** |
| 探针查询集（A/B/C 组） | Phase 5（六元组查询接口之上） | 材料版提供通用接口，OptionBench 在其上写业务查询——接口与查询内容分离 |
| 只读事件流导出 | Phase 5（已列入任务表） | 评测/审计/通用可观测性共用 |
| TMS 模拟（D1 ground truth） | Phase 2 TMS 能力复用 | Seine 差分验证登记为其验证工具（WP7 可选） |
| **多 baseline 隔离** | **Phase 5（查询接口支持 baseline_id 分区过滤）+ 测量实例分区部署配置** | 配置项而非新代码；防 C3 探针假阳性 |
| SPS/ORS 计算支持 | 完整产品（随 OptionBench M5–M7） | 评分器属 OptionBench，memory-core 只供数据 |
| HTTP API 端点规范（5 工具 REST 映射 + 事件流端点 + 认证） | **待立项**：Phase 4 由子课题1 起草 | OptionBench 原生模式 Python baseline 依赖 |

**侧车（sidecar）归属**：镜像 sidecar 归 **OptionBench 环境工程**（M2–M4 任务流构造器同期开发），不是 memory-core 组件；其**输出契约 = 材料版事件 schema**（材料版定契约，OptionBench 写采集器，互不重复）。

**时间线依赖自检**：① **设计对齐**——事件 schema 最小集（Phase 2，W5–6）先于 OptionBench M2 接入协议定稿（≈W5–8）；② **运行就绪**——batch（W2 末）、audit 模式（Phase 2）先于 sidecar 实际写入（M3 起，W9+）；③ **探针查询**——Phase 5 通用接口（W13–14）与 OptionBench M3 启动（W9+）节奏吻合；④ **原生模式**——HTTP API 规范（Phase 4 立项起草）先于 B1+M 消融（OptionBench M5）。无断档、无重复。
